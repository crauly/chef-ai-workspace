# ADR-009: 食材・仕入先・価格変動支援を中核として実装する

日付：2026-10-29。状態：製品方針はユーザー確認済み。具体的なデータ契約・運用値は設計レビュー待ち。実装済みの意味ではない。

## 背景と訂正

中小・個人飲食店は、レシピだけでなく使用食材、購入先、価格の変動を十分な人手で継続管理しにくい。本製品は、その負担をMuseの判断支援と簡便な会話操作で軽減する。音声文字起こしは入口である。

10/27マージ済みPR #5の[設計判断](IMAGE_STORAGE_DECISION.md)は、音声だけで共通食材を登録・選択・再利用してレシピ材料へ紐付ける受入条件を持つ。[設計契約](CORE_CONTRACTS.md)にもlink/unlinkがある。これを新規拡張と説明した前回の整理を訂正し、未実装の既存要件として扱う。「リンク任意」は未登録でも使えるための経路であり、リンク機能を省略する根拠ではない。

仕入先別価格、価格確認、値上がりの通知、Webで約3候補の代替商品/購入先を提案する意図は、2026-10-29のユーザー発言で明確に再確認された。過去の全会話からその詳細を発見済みとは主張しない。旧文書の「本格的な仕入先管理はMVP対象外」を、これらの中核支援を省く理由にしない。

## 決定

1. レシピ材料行、実使用食材、仕入先、仕入先の商品/購入条件、時点付き価格を区別する。食材をレシピごとに複製せず再利用する。
2. 新規の実食材は確認保存時に台帳へ登録し、材料行を紐付ける。既存食材はIDで再利用する。生の誤認識を即確定登録しない。レシピ/台帳の一方だけ残らない保存境界と再送対策を設計する。
3. 食材には銘柄・規格・仕入先・購入価格を扱える構造を持つ。同じ商品でもAmazon、楽天、スーパー等の購入先・条件を分ける。名称だけで異なる商品を統合しない。
4. 価格の観測履歴を保存し、現在の採用価格、前回購入価格、Webで見つけた参考価格を混同しない。価格更新が関連レシピの現在原価に与える影響を示す。過去の保存版は変更しない。
5. 価格変動をベル通知で知らせ、対象食材と使用レシピへたどれるようにする。通知既読は価格の採用や仕入先変更の承認ではない。
6. 必要時にWebから約3候補の購入先/類似商品を調べて提案する。出典URL、確認時点、規格・送料等の比較条件、不確実性を示す。実在する検索手段/取得条件を検証し、架空APIや価格で代用しない。候補不足なら不足を明示する。
7. Muse Sparkは世界の料理・食材・流通商品に詳しい商品管理担当兼レシピ管理補助として、会話状態と所有者の台帳/過去レシピ/価格出典を使い、意図・候補・不足質問・変更案を返す。事実の価格やIDを知識だけで作らない。
8. アプリが権限・型・単位・整合・計算・保存を担う。Human Gate、所有者分離、版競合、べき等性を維持する。発注/購入/仕入先切替や価格採用をモデルだけで実行しない。
9. 材料名は内部に保持し、画面は紐付け実食材名を主表示、材料名を補助表示する。未登録・仮設定・未確定の経路を残し、未確定の原価を完全な総額と表示しない。

## 未決事項：推測して実装しない

- 価格確認の契機（ユーザー指示、レシピ閲覧時、期限経過後、定期実行）、間隔、対象件数、費用上限。
- 通知の閾値・基準価格・頻度・再通知条件。常時監視や自動購入は決定していない。
- 採用価格の切替に必要な確認と、inherit/overrideの既存契約との接続。
- 外部検索/価格取得の利用可能な手段、商品サイトの条件、取得できない場合の復旧。
- 食材と仕入商品/オファーの具体的な識別キー、既存未リンク材料の移行方法。

これらは[実装計画のG0](IMPLEMENTATION_PLAN_MASTER_PRICE.md)で解決し、未確定値を勝手な既定値として本番へ入れない。本格的な在庫・発注・会計・仕入先API一括同期は、現在の中核要件を置き換えるものとして増設しない。

## 2026-11-04 追加決定：規格・購入元別価格・レシピ原価連動

この節は既存の実装済み契約を更新する製品判断である。各要素の実装・DB適用・本番E2Eの完了を意味しない。ADR-015 の価格SSOT方針と併読する。

1. **商品と規格**：`ingredients.id` が具体的な食材商品の一意ID。食材名と自由入力の規格 `ingredients.spec` を別フィールドで保持し、一覧・編集・検索・候補識別で併記する。名称と規格の一致だけでは商品同一性を断定しない。異なる商品・メーカー・規格は別の食材IDを許す。規格は表示・識別用であり、包装の「1パック10個入り」からのレシピ単位換算や原価換算を暗黙に行わない。
2. **関連**：レシピ材料は `ingredient_id` と任意 `supplier_id` を保持する。食材IDは使用する商品、仕入れ先IDはどこから購入する条件かを指す。`offers` は `ingredient_id` と `supplier_id` を結ぶ購入条件で、`price_observations` は `offer_id` ごとの購入・手動・外部参照価格の観測履歴。仕入れ先マスター自身には価格を持たせない。
3. **採用価格と原価**：レシピ材料に仕入れ先が指定されている場合、同一食材×指定仕入れ先に**明示採用された**価格を単位・数量検証後に現在原価へ反映する。単純な最新値や最安値の自動採用は禁止する。仕入れ先指定時に該当採用価格がない／複数の購入条件が曖昧／数量換算不能なら partial とし、無関係な仕入れ先や共有価格を静かに転用しない。仕入れ先未指定では既存 `ingredients.current_price` の明示採用価格を用いる。履歴の追記は採用・価格変更と別操作。保存版の過去原価スナップショットは変更しない。
4. **相場参考価格（下記「承認済み新規保存」で更新）**：当初の既定の UI 選択肢は「相場参考価格（仕入れ先なし）」。これは実在しない店舗を作成するのではなく `supplier_id=NULL` に対応する。平均／市場参考値は条件・対象件数・取得時点・出典を示し、実仕入れ額と別の参考価格として扱う。参考値を計算に採用するには人間の明示承認が必要。
5. **軽量性**：スマホでの食材検索・識別・価格選択を優先。本格的な包装換算、在庫、発注、購入自動化は本件で導入しない。
6. **正式経路**：Human Gate、owner整合、単位マスターの確定変換のみ、価格採用とレシピ保存の承認経路を守る。通常の `ingredient_id` リンクを `offer_id` に置き換えず、複数オファー時の採用はIDで確定して曖昧な名寄せをしない。

受入：規格の CRUD/検索、相場参考価格の既定表示、仕入れ先別価格観測・採用、同一食材で仕入れ先変更時の原価再評価、採用なし/曖昧/単位不一致の partial、旧保存版不変、owner/RLS/Human Gate回帰をテストする。

## 2026-11-04 実装契約補足：レシピが選択する購入条件ID

- レシピ材料は `ingredient_id`（食材識別）、`supplier_id`（仕入れ先識別）、任意の `offer_id`（具体的な購入条件識別）を区別して保存する。食材IDをOffer IDに置換しない。
- 同一食材・同一仕入れ先に複数の購入条件がある場合、`supplier_id` だけでは単価を決めず、`offer_id` を明示選択する。未指定で複数の採用候補があれば原価は `partial` とする。最安値・最新値を勝手に採用しない。
- `offer_id` が明示されている場合、採用済み観測 `adopted_observation_id` のあるそのOfferのみを原価に用い、該当なしは `partial`。別Offerや相場参考価格への暗黙代用は禁止。
- レシピの仕入れ先切替では以前の `offer_id` を消去する。購入条件まで指定されたときは owner/ingredient/supplier の整合をDBトリガーでも検証する。
- 価格の採用は既存の承認済みOffer価格操作に限定する。レシピの材料価格編集から仕入れ先別価格を直接上書きしない。
- 食材が仕入れ先未指定のときは従来の食材マスター採用価格を参照し、過去保存版は有効価格のスナップショットを保持する。
- 2026-11-04の変更はPR #125（`feat/ingredient-spec-supplier-pricing`）上のコード変更であり、SQL適用・自動テスト・実DB E2Eの完了宣言ではない。既存の `202611040001`〜`0003` との番号衝突回避のため規格SQLを `202611040004` とする。

### PR #125 レビュー修正

- 数量 `3500` / `3500.0` などは同じ数値の購入条件として再利用する。単位換算や複数Offerの自動統合は行わない。既存の数量が数値以外なら一致対象から除外する。
- 食材の一意制約も管理RPCに合わせて owner・正規化名称・正規化規格とする。規格違いの同名商品は別IDを持てる。
- 価格影響・通知詳細の試算も現在原価と同じowner別採用価格・単位マスターを用いる。対象外の仕入れ先／Offerは維持し、未解決価格の暗黙補完はしない。
- 適用済みの `0004` / `0005` は書き換えず、追加マイグレーション `202611040006` / `202611040007` で修正する。実DBへの追加適用はマージと別途管理する。
- `Python core tests` の手動ワークフローに一時PostgreSQLでの全マイグレーション適用とSQL回帰チェックを追加した。`tests/sql/bootstrap.sql` はCI専用で、実Supabaseには適用しない。


## 2026-11-04 追加決定：承認済み新規保存と抽象仕入先の実ID

ユーザーの明示選択により、上記の相場参考価格 `supplier_id=NULL` 方針を更新する。
曖昧なWeb検索・平均価格を紐付ける抽象仕入先として、ownerごとに実際の
`suppliers` 行「相場参考価格」を1件用意する。Amazon等の指定先は別のSupplierとする。
これは新しい独立マスターや独立価格テーブルではない。検索で得た価格は自動採用しない。
仕入れ先管理は保存先の管理、購入先候補は出典・条件を伴う提案を担当する。

- 正式な新規保存は `/demo/recipes/full` の明示承認を入口とし、
  `create_owned_procured_recipe` が既存の `create_owned_recipe` と
  `set_owned_offer_price` を同一トランザクションで呼ぶ。既存のowner／単位／食材参照
  ガードを通し、レシピ・新規マスター・Offer・採用観測・初版スナップショットを一括保存する。
- 音声下書きの `supplier` は保存時にowner内の前後空白除去・大文字小文字を無視した名前で照合する。
  一意な既存行を再利用し、なければ承認時に登録する。曖昧な重複は409で全体を拒否する。
  価格3項目の全件入力／未確定時nullの境界は変えない。
- 入力した有効な購入価格は承認済み観測として既存Offer価格採用経路に渡し、購入数量・単位の一致する
  Offerを材料の `offer_id` に固定する。同一食材でも仕入先・購入条件が違えば別のOfferを持つ。
  指定先の採用価格がない場合はpartial、複数条件の自動選択・別仕入先への代用・ゼロ補完は禁止する。
- 仕入先省略時は実IDの相場参考価格へ紐付ける。既存の明示承認済み共有価格は再利用できるが、
  推定価格や別の実仕入先価格を借用しない。原価用スナップショットも同じトランザクション内で確定する。
- `request_id` と正規化JSONのハッシュで再送を検証し、同一内容では重複登録・再採用しない。
  同じIDで内容変更は409。旧作成データのハッシュ未保持分は従来の再送動作を維持する。
- システム既定行は移行時、または新ownerの仕入先一覧取得／承認保存時に冪等登録する。
  これはユーザー指定仕入先や価格を承認前に登録する動作ではない。既定行の改名・削除をDBで防ぐ。
- 旧NULLのOfferはID・価格履歴を維持して抽象仕入先に移す。既存レシピstateと保存版は変更しない。
  旧NULL材料は従来の `Ingredient.current_price` を参照し、抽象仕入先の明示採用時に共有価格も更新する。
  実仕入先の価格採用では共有価格を変更しない。

適用手順・重複点検・未確認事項は [承認済み仕入保存](APPROVED_RECIPE_PROCUREMENT.md) を参照。
本番SQL適用・本番動作・実際のWeb検索の確認完了は、この実装の完了とは区別する。
