# 音声レシピ作成フローの契約と検証

2026-11-05。下書き表示、価格調査、正式保存を分離する。ADR-011末尾の決定を実装し、既存のStructured Output・Ledger-first・Human Gate・原子的保存RPCを使用する。新しいマスター体系・ジョブ基盤・外部検索サービスは追加していない。

## 処理と失敗時の振る舞い

- 音声認識済み発話は受信時点で端末の作業下書きへ保持する。解析中の追加入力もキューに保持し、検証済みの先行下書きと未解析の差分から次を解析する。モデルへ送る前回状態はレシピの事実と未完了依頼だけで、検索の出典本文や候補一覧を再送しない。
- Muse解析には共通20秒の上限を設ける。タイムアウトや通信障害の自動リトライを廃止。不正構造のみ一度再生成できるが同じ時間予算を使う。既存レシピを空のJSONオブジェクト相当で消す応答も拒否。失敗時は発話と正常な下書きを保持し、未解析発話がある間は保存しない。
- 下書き表示にマスター照合は不要。未確定値は空文字で保持し、保存時の投影ではnullとする。標準単位の既知分類は提案できるが、未知の換算係数は作らない。
- 価格調査依頼の対象件数を3件に切らない。既存フォームの最大40行まで対象を保持し、画面は2対象ずつ検索して全対象の結果・失敗を順次表示する。共通処理は最大3並列。台帳3秒・検索45秒の上限があり、1バッチ失敗でも後続を進める。
- 対象はSparkが現在の下書きと自然文から決める。カテゴリ依頼を単純な「全部」一致で全食材へ拡大しない。台帳の別食材を勝手に採用しない。名称・仕入先を検索結果の同一性条件に含め、数量訂正とは並行できる。出典・購入数量・単位を持つ未承認候補として表示する。
- 最初の保存指示は読取専用の `/api/recipes/full/review`。食材・単位・仕入先の再利用／作成と採用価格変更を表示する。次の明示保存指示または承認ボタンが既存 `/api/recipes/full` を呼び、同じ検証を再実施して原子的に保存する。途中の訂正・価格到着は古い確認を無効にする。音声は既存の録音epoch検証を使用する。

## 確認した原因

1. 音声解析は25秒の呼び出しを最大2回行い、失敗時に約50秒待つ構造だった。
2. 価格調査は組み立て時とAPI受付時の両方で3件に制限されていた。
3. 実Meta検索でHTTP200でも `status: incomplete / reason: max_output_tokens` を再現した。2048枠の中で検索・説明を続け、候補JSONが途中で切れていた。候補1〜3件・検索の収束・説明抑制を指示し、4096へ調整した。「えのき」は調整前24.3秒でincomplete、調整後12.4秒でcompleted・出典付き候補を取得した。これは個別測定であり、一般的な平均速度ではない。
4. 新規ユーザーの単位カタログが空の場合、標準g/mlも新規候補として次元確認が必要だった。安全な既知分類を候補に設定し、承認後の同時登録で解消した。

## 検証結果

初回の実Muse単独確認では10材料、しめじ30→20g、メーカー・仕入先、全10件の依頼を9.1秒で構造化。後続のえのき25g、ブラウンマッシュルーム、雪印・スーパーBへの訂正を5.9秒で反映した。正常JSONだけでなく、その後の画面・検索・保存・再読込は同じ受け入れテストで確認する。

最新コードの実Muse計測では初回8.343秒、訂正7.952秒（Server-Timing）。別途、実Museで次の対象範囲を全件確認した。再実行は `cd web && CHEF_LIVE_RECIPE_FLOW=1 node --test tests/voice-scope-live.node.cjs`。
