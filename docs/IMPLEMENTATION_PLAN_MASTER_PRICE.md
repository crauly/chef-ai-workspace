## G0で潰す項目

- [ ] 食材/商品/仕入先/価格のID・必須/任意項目と名称重複の扱い。
- [ ] レシピと台帳を一体保存するトランザクション、同時編集・再送・旧API互換。
- [ ] 未確定を残した保存の状態と承認条件、inherit/override/価格採用の操作契約。
- [ ] 旧未リンク材料の候補化・確認・移行、現価格/保存価格の表示規則。
- [ ] 価格確認の契機/間隔/対象/費用上限。通知の基準/閾値/頻度/既読。
- [ ] 利用可能なWeb取得手段・認証/条件・規格比較・失敗時経路。未検証APIを仕様化しない。
- [ ] 短い聞き返しの画面/音声方式、ASR区切り/遅延/キャンセルの受入。
- [ ] 大会向けの段階的な範囲・順番をNotionで合意。中核を黙って削らない。

依存しない契約調査は進めてよいが、未決事項に依存する実装/本番適用は止めて、論点と選択肢を記録する。

## 必須の受入シナリオ

- A1 新規商品を仕入先/規格/価格と会話登録→確認→レシピ/食材台帳に保存→再読込。
- A2 別レシピで「前のペペロンチーノと同じパスタ」→同じ食材ID/正しい価格出典で再利用。
- A3 同商品を別仕入先で登録→別購入条件を保持。名前だけで別商品/規格を統合しない。
- A4 「国産、いやイタリア産」など連続訂正と断片入力→現状態へ反映。不足項目だけ質問。未確定のまま保存する経路も確認。
- A5 比較可能な値上がり→ベル→影響する材料/レシピと現在原価差。保存版価格/原価は不変。
- A6 Web調査→出典付き約3候補→採否確認。取得不能/規格不明/候補不足時は捏造・自動採用しない。
- A7 失敗/再送/同時編集/所有者A-B/古い音声承認/キャンセル/再開で、誤保存・孤立行・勝手な価格変更がない。
- A8 実音声→実Muse→専用DB→保存/再読込を確認し、ユーザーが報告した実会話で再評価。fixture成功で代用しない。テスト所有者の後片付けを記録。
