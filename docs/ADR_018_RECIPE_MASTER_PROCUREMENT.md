# ADR-018: レシピ登録・編集を食材マスターと仕入条件へ接続する

日付：2026-11-05。状態：実装・ローカル検証。本番適用は別途。

## 確認した問題

レシピ編集は `set_material_price` を仕入先付き材料で拒否していた。仕入先なしの編集も食材の `current_price` だけを更新するため、Offer採用・観測履歴と一致しなかった。手動追加フォームは価格の全項目を必須とし、音声登録の価格未確定契約と異なっていた。新規登録は完全一致だけを照合し、類似名・規格違いの選択を提示できなかった。

一覧取得・保存は現行スキーマを必須とする。未適用の移行はリリース時に適用し、旧スキーマへフォールバックしない。

## 決定

1. `ingredients` を正式な食材マスターとして維持する。完全一致が一意なら再利用、複数候補や類似表記なら選択を要求する。類似度は候補提示だけに使用し、自動統合しない。別の食材として登録する選択と規格入力も提示する。候補はowner内に限定し、一要求の照合で取得済み候補を再利用する。
2. 新規登録は既存 `/recipes/full/review` → `/recipes/full`。材料に任意の `ingredient_id`、`new_master`、`spec` を追加し、選択を保存に渡す。選択なしの曖昧保存は拒否する。現行の全入力を作成ハッシュに含め、同一要求の再送を検証する。
3. 編集は既存 `/recipes/{id}/confirm` と `commit_recipe_crud` を維持する。新しい `/confirm/review` は同じPython準備処理を読み取り専用で実行し、全食材の再利用/作成/候補と変更後の使用量・採用価格を返す。保存経路は増やさない。手動編集・追加、AI/音声編集はこの照合結果を提示し、未選択の候補がある間は承認を拒否する。
4. 編集モーダルで食材名、使用数量/単位、仕入先、購入数量/単位、価格を扱う。仕入先付き材料も価格編集を許可する。確認画面に対象の仕入先・購入条件・価格、他レシピの現在原価への影響を表示し、明示承認後に保存する。
5. `commit_recipe_crud` の既存引数内の食材エントリへ `purchases`（材料ID・仕入先ID・承認済みquote）を渡し、既存 `set_owned_offer_price` を同じトランザクション内で呼ぶ。owner・単位・価格妥当性を検証し、レシピのOffer参照も更新する。履歴・採用ポインタ・相場参考価格の共有価格規則を再利用する。仕入条件は食材/仕入先/数量/単位で区別し、同一条件の矛盾価格は全体を拒否する。
6. 同じ採用価格を明示送信しても観測は増やさない。要求ID・ハッシュ・revision CASを維持し、失敗時は食材・仕入条件・価格・レシピ・receiptをすべてロールバックする。新規保存版の原価と採用quoteはDBの採用後状態から計算し、過去の保存版は変更しない。
7. 使用数量は材料行固有。共通マスターへの改名や他レシピの使用量変更をレシピ編集から暗黙に行わない。別マスターを選んだ場合は旧Offerを引き継がず、明示された仕入条件だけを新しいマスターへ適用する。
8. 価格未確定の追加は既存 `add_unpriced_material` を使う。0円を補わない。単位マスター取得失敗は追加フォームに理由を表示する。単位・仕入先・価格・競合・DB失敗は安全なコードで案内し、入力を保持する。
9. 設定の名称は「食材マスター」に統一。既存の全件取得・検索・ページングを維持し、絞り込み解除を追加。共有価格は「共通価格」、仕入先別価格は仕入先名と購入数量/単位を表示し、別仕入先の価格でレシピ原価を代用しない。

## 音声内容の欠落対策

後続解析で既存材料が一部だけ欠落した場合も、正常なJSONとして下書きを置換しない。MuseのStructured Outputに `material_changes`（以前の名前、remove/rename、変更後名）を追加する。ハーネスは消えた既存行に対応する変更宣言、改名先の存在を検証し、不足時は既存の時間予算内で修復、失敗時は既存下書きを保持する。削除・改名は解釈表示にも出し、Human Gateで確認する。写真取り込みは以前のスキーマを維持する。

初回解析から抜けた食材の有無をJSON構造だけで保証することはできない。認識発話と全食材一覧を提示し、マスター確認でも件数と全行を示す。DBにない音声・端末下書きまで調査済みとは扱わない。

## 移行と検証手順

正規移行：`supabase/migrations/20261104171528_recipe_master_procurement.sql`。既存の `commit_recipe_crud` と `create_owned_recipe` の同一シグネチャを置換する。前者は既存の正式採用RPCを利用、後者は明示承認された別規格の登録を許容する。新テーブル・新しい保存RPCは追加しない。service_role限定、owner検証、search_path固定を維持する。

先行するADR-017の移行を含む全移行が前提。互換処理は設けない。本PRでは本番移行・マージ・デプロイを行わない。リリースではDB移行を先に適用する。

```bash
.venv/bin/python -m unittest discover -s tests -q

cd web
CHEF_TEST_PGPORT=55447 npx playwright test --config playwright.recipe-master-pg.config.ts

```

使い捨てPostgreSQLへのbootstrap・全移行適用手順はADR-017とCIに従う。本番接続でテストfixtureを実行しない。

## 検証結果・限界

- ブラウザ→Next→FastAPI→実ローカルPostgreSQLで、グアンチャーレ・ペコリーノ・ディチェコパスタ・鶏卵の4行を登録。類似表記の既存マスター選択、別商品の新規登録、承認、マスター画面での検索、仕入先付き価格の変更、別レシピへの原価反映、再読み込み、価格なしの黒胡椒追加まで成功。
- 実DB APIテストで仕入先/購入条件の非干渉、保存版保持、同一要求再送、途中の価格INSERT故障による新マスター/レシピ/receiptの全体ロールバック、価格未確定追加、候補未選択拒否を検証。新規DBへ全移行と既存SQL検証も成功。
- 実MuseをDBから隔離して呼び出し、初回HTTP200/8150ms、訂正HTTP200/7579ms。全4食材を保持し、パスタ120gとグアンチャーレ仕入先「自家製」を反映。実モデル出力を正式な入力変換後にローカル実DBのreview→保存→再取得へ渡し、鶏卵を含む4行と全マスターの一覧表示を確認。
- 実モデルと実DBは分離した検証。実ブラウザの一巡は音声認識/解析結果をfixture化している。実マイク・実端末・公開サービス上の通し操作は未検証。過去の鶏卵欠落の原因や既存データの修正完了を主張しない。
