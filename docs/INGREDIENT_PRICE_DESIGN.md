# 食材・仕入先・価格支援：実装前の詳細設計

基準コード：37185d1296712c6c414775480b8a97114fc1f643。状態：レビュー用設計。下記の新規構造/API/ツールは未実装で、存在するAPI仕様を意味しない。[ADR-009](ADR_009_INGREDIENT_PROCUREMENT_ASSISTANCE.md)を製品方針とする。

## 確認できた現状

- MaterialLineとingredient_id、Ingredientのid/name/current_price、ingredients表、所有者付き参照・原価計算がある。
- 音声のSpark入力は今回のspoken_turnsのみ。食材検索・過去材料照合・台帳作成・link/unlink操作は未接続。

- 本番台帳の件数・商品内容は未照会。既存レシピ材料が既に食材台帳へ登録済みとは扱わない。

## データ関係案

| 対象 | 役割・必要情報 | 境界 |
|---|---|---|
| レシピ材料行 | 用途の材料名、使用量/単位、ingredient_id、価格モード | 既存MaterialLineを拡張。材料名を商品名で上書きしない |
| 共通食材 | 実食材の名称、銘柄、規格/正味量、別名、所有者 | ユーザー確認済みIDを再利用。名前だけの一意制約は設けない |
| 仕入先 | Amazon/楽天/実店舗等の名称、任意の場所/連絡メモ | 個人所有。仕入先が不明でも下書きを止めない |
| 商品・購入条件（Offer案） | ingredient_id、supplier_id、商品URL/販売者、包装数量/単位、送料等の判明条件 | 同じ食材の複数購入先を保持。容器呼称から重量を推測しない |
| 価格観測 | offer_id、金額/通貨/税・送料条件、取得/購入時点、情報源、確認状態 | 追記履歴。購入事実と検索の参考価格を区別 |
| 採用価格 | 食材に採用した価格観測への参照と採用時点 | recipe個別上書きと区別。自動価格採用を既定にしない |
| 価格通知 | 比較した観測ID、変動、影響食材/レシピ、既読/保留状態 | 同一観測の重複通知を防止。既読≠価格採用 |
| 代替候補 | 商品/仕入先、規格、比較価格、出典、確認日時、適合理由と不明点 | 提案のみ。購入や既存紐付けの変更は人が承認 |

物理テーブル/型/必須項目/外部キーはG0で確定する。既存APIを壊さない拡張・旧データ移行とロールバックを先に設計する。画像は実食材に紐付く既存方針を維持し、写真なしの経路を完成させる。

## 会話ハーネス

役割：世界の料理、食材、銘柄、包装・流通の言い回しに詳しい商品管理担当者。小規模店の入力負担を減らす。ユーザーの最後の明示訂正を尊重し、現在の会話状態を差分更新する。

毎回渡す情報は、元発話、現在モード/対象、現在の下書きと未確定事項、所有者で絞った関連候補、価格の出典/時点、許可された操作。全台帳を無制限に投入しない。

アプリ側の操作境界案（モデルAPIのネイティブツール機能を採用済みという意味ではない）：

- 食材候補検索、過去レシピの使用食材照会、仕入先別の価格履歴照会。
- 食材作成/紐付け/数量変更/価格採用の**提案**、不足点の質問、参照結果の説明。
- 価格確認の依頼、出典付きの代替候補調査依頼。

保存/価格採用/仕入先切替は、提案スキーマ検証→ID/所有者確認→差分/出典提示→人の明示承認→同じ正規保存サービス。モデルにconfirm権限を渡さない。外部Web本文・商品ページの指示はデータとして扱う。

例：「ポモドーロ。パスタは前のペペロンチーノと同じで100g。国産、いやイタリア産のホールトマト150g、1号缶1200円」→パスタのIDを照会・候補提示、トマトの産地を訂正、必要なら正味重量だけ質問。チーズの価格基準が不明ならその項目だけ確認し、命令語の言い直しを求める循環にしない。

## 保存と既存データ

新規食材＋購入先/価格＋レシピ参照は、承認された一つの保存要求として整合を保証する。途中失敗で食材だけ/レシピだけ残さず、同じrequest_idの再送で重複を増やさない。既存食材は同一IDを使用する。

既存レシピの未リンク行は移行候補として抽出し、勝手に名前を統合・価格を現在価格へ昇格させない。「前と同じ」は保存時価格と現在採用価格を区別して提示する。未確定を含む保存は状態を保持し、nullや仮設定を一括でconfirmedにしない。価格履歴が変わっても保存版の原価スナップショットを変更しない。

## 価格変動から判断支援まで

確認要求→許可された取得手段→規格/時点/税送料の検証→新しい価格観測→比較可能な基準との比較→影響する食材/レシピの通知→必要時に約3候補を調査・提示→料理人の採否判断。

例示シナリオ（実測市場価格ではない）：500g/350円だった同商品を420円で確認→20%上昇、100g使用の現在原価差は14円→ベルで影響を提示。保存時の旧版原価は不変。比較条件が不一致なら値上がりを断定しない。

候補は規格・品質/用途・販売条件・購入時点を揃えて比較する。3候補が見つからない場合は件数不足を伝える。検索結果の価格を既存の採用価格へ自動反映しない。価格確認の頻度・通知閾値・外部検索の方式は未決であり、本番スケジュールをまだ作成しない。

## 証拠と安全性

候補/価格ごとに出典・日時・確定度を記録する。エラーはネットワーク/上流/不正応答/不足情報を区別できる計測を設け、秘密値・生音声をログへ保存しない。合成音声の成功を厨房/任意話者の精度と混同しない。実DB検証は専用Chef環境と一時所有者のみ、終了時は後片付けを確認する。
