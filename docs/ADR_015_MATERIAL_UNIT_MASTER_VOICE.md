# ADR-015（設計案）: 音声から材料・食材・単位マスターを一体的に扱う

Status: **Proposed / 未承認**（2026-11-03）。ADR-009・CORE_CONTRACTS・既存Supabase構造を置き換える決定ではない。

## 製品目的

料理人が「さくら卵Mサイズ3個、20円/個」「鶏もも肉、○○地鶏」などと自然に話し、誤認識があっても必要な行だけ短く訂正して保存できる。途中の曖昧さを理由に会話を何度もやり直させない。単位・食材・価格の根拠を捏造せず、最終的な人間の明示登録によって正しい保存状態に近づける。

## 実装現状と契約上のギャップ

- `MaterialLine` は現在、各レシピ版の行データであり、共有の「抽象材料」マスターではない。
- `ingredients` は共通の具体食材。ブランド、規格、別名、採用価格の列を持つが、Voice `/demo/recipes/full` は `ingredient_id` を付けず、共通マスターの検索・新設・紐付けを行わない。
- `offers`, `suppliers`, `price_observations` は別管理。Supplier UIだけでは材料・食材・購入条件の階層を編集できない。
- 旧CORE_CONTRACTSはレシピ表示名として `material_name` の保持を規定、ADR-009はリンク実食材の主表示を規定しており、表示のSSOTについて再合意が必要。今回のユーザー説明は「レシピには抽象材料名を主表示」。既存画面の `display_names` はリンク食材を主に選び得るため現状と相違。
- 単位は `g/kg/ml/L` の固定集合を音声パーサーとFull Recipe APIで検証していた。実演中の `個` を拒否。PR #114 はこの直接の障害を先行修正するが、Unit Masterは含まない。

## 提案する責務

1. **Material Master（抽象材料）**：例「鶏もも肉」「卵」。名称、別名、カテゴリ。料理用語の揺れを吸収するが、銘柄や仕入先で同一商品だと判断しない。必要になる場合だけ所有者単位で登録し、既存レシピ行とは別に保持。
2. **Ingredient Master（具体食材）**：「○○地鶏もも肉」「さくら卵M」。`material_id` は必要なら参照。ブランド・規格を維持し、同名異規格を勝手に統合しない。既存 `ingredients` に互換拡張。
3. **Recipe MaterialLine**：使用数量と単位、`material_id` / `ingredient_id` の任意リンク、価格モード、承認状態を保持。抽象材料名を主表示する方向を検討するが、表示規則は現行 `display_names` の契約確認後に確定する。未リンクのままでも保存可能。
4. **Unit Master**：正式記号、表記別名、次元（mass/volume/count/unknown）、所有者と登録由来。QuantityとPriceQuoteは同一の正規単位IDに参照可能。既存unit文字列は段階的移行で保持し、直ちに壊さない。
5. **Conversions**：kg→gなど確定済みの換算のみ共通規則。個→g、尾→g、サイズ換算は商品別の根拠がない限り禁止。
6. **Offer / Supplier / PriceObservation**：既存の仕入商品、購入先、価格履歴を温存。新マスターとの連結は外部キーの所有者整合・過去の価格スナップショット不変を保証。

## 音声ハーネス・保存経路（案）

`発話→Museの構造化提案→所有者別候補検索→単位正規化・材料/食材候補照合→下書き表示と差分訂正→一度の明示登録Human Gate→サーバーによる原子的なレシピ/マスター/link保存→再読込`。

Museは食材名・ブランド・規格・単位の文脈解釈と複数候補の提示を担う。新規マスターの登録案は下書きとして保持し、永続化は正規承認経路で一回だけ。既知の単位・所有者確定の食材ID再利用は不要な対話を増やさない。曖昧な複数候補がある場合のみ短い選択を要求。誤認識を訂正した場合は変更行とリンク候補だけ再計算する。

## 未決・移行のゲート

- 実食材が必ず1つの抽象材料に属するか／複数分類を許すか
- `material_id` と `ingredient_id` の関係を保存版にどうスナップショットするか
- グローバル標準単位と所有者固有単位の衝突、エイリアスの曖昧性
- 未知単位の新規登録はレシピ承認と同時とするが、同一表記衝突・撤回時の処理
- 既存の未リンクレシピ行の移行（名前の自動統合はしない）
- 既存 `save_recipe_with_ledger` の承認証跡・冪等性・所有者確認を通した新規マスター登録。直接 `/demo/recipes/full` から脇道を書込可能にしない
- 過去の原価スナップショットは変更しない。価格観測の採用と表示・再評価を別操作として扱う。

## 最初の実装順

1. PR #114で個数単位の登録障害を解消し、数量・単位基準が一致すれば原価計算し、違えばpartialにする回帰テスト。
2. 正規のレシピ/台帳保存経路の確認と、抽象材料のSSOTおよび表示契約の確定。
3. DBマイグレーション・owner整合・Unit Masterの検索/候補API/テストを小さく追加。
4. 音声による候補照合と下書き訂正・一括承認保存、食材マスター閲覧・修正UI、実DB E2E。
